# 需求对照与设计说明

依据：《基于生产管理访谈录音与会议笔记》（2026-10-19）的 8 个业务主题、9 步目标流程，以及访谈录音和会议笔记。

文档中标 ★ 的条目，是录音中没有提到、由我方补充的功能。

> **状态说明（2026-10-20）**：本版已按外部评审修订 5 条业务规则（图纸绑定、2 天节点、冻结与调料、行级冲销、供需依赖），并补了生产启动隔离、并发防重、客户展示权限、AI 责任边界。修订与验证结果见第六节。**在客户用真实数据做完试运行验收之前，不表述为“全部需求已实现”。**

## 三、关于 AI 接口：保留，但只做辅助，默认关闭

- **核心逻辑不依赖 AI**。齐套、冲填、锁定、库存、审批全部是确定性程序，结果可以复现，也能审计。AI 输出不稳定，不能用来决定预占给谁、能不能开工。
- **保留的 3 个辅助场景**，都是只读、只给建议：
  1. 缺料与交期风险日报的文字摘要；
  2. 来料异常辅助分析：只给“可能原因 + 待核实证据 + 参考处置”，**不判定责任方**，责任认定与处置由审批人依据证据决定；
  3. 基于系统数据的问答，例如“本周哪些订单可能逾期”。**问答只带当前账号有权看的数据**（车间账号看不到客户和订单明细），AI 不能借问答越权。
- **可插拔**。接口采用 OpenAI 兼容协议，DeepSeek、通义千问、智谱，以及本地的 Ollama、vLLM 都可以接，改配置就行。如果对数据外发有顾虑，可以部署本地模型，数据不出厂。
- **能降级**。没有启用 AI 或者调用失败时，自动改用规则或模板生成结果，业务流程不受影响。每次调用都会记日志。
- 为什么默认关闭：客户的需求里没有 AI 诉求，先把确定性的业务跑稳；以后客户想用，管理员在界面里打开即可。

## 四、齐套引擎规则

1. **排序**：已下达或装配中的订单排在前面，然后依次按人工置顶、优先级、需求日、单号排序。
2. **需求**：单位用量 × (1 + 损耗率) × 订单数量 − 已领数量。
3. **供应分配**，按以下顺序：
   1. 人工锁定的库存；
   2. **在制自制任务 / 本厂供料外协单尚未领用的原料**先从库存、在途里扣出（原料不再被当成空闲库存；原料不够则这些任务的产出可用日顺延或标记无法确定）；
   3. **已冻结给本订单的库存**（按订单优先级，库存不够时低优先级先让出）；
   4. **空闲库存**：只分配没被冻结的部分（冲填）；
   5. 专属本订单的在途（按单采购或按单加工）；
   6. 公共在途，按可用日先后分配。
4. **还不够时**：如果这个物料有下级 BOM，就把缺口向下级展开（逐层 MRP 净算），预计可用日 = 下级最晚到齐日 + 加工提前期；如果没有下级 BOM，就记为缺料。订单若已由加工任务/外协供应成品件，就**不再向下展开原料**，原料只被该任务认领一次，不会重复计算。
5. **状态判定**：在途物料的**可用日**（预计到货日 + 检验/转运天数；自制件为计划完工日）≤ 需求日，记为“在途可齐”；晚于需求日，记为“在途延误”。缓冲天数（默认 2）只决定“开工前检查”预警何时触发，不是到货要求。
6. **齐套率**：按品项计算，即已齐的品项数 ÷ 总品项数。不按数量计算，避免螺栓这类大数量物料把比例拉偏。
7. BOM 有循环引用时，生效前会被拦截；计算过程中遇到循环也不会无限递归。

## 五、已知边界与后续建议

- **未做**：财务成本核算、MRP 自动排产（目前由计划员指定计划开工日）、工序级报工、PDA 扫码。这几项都可以作为二期内容。
- **DWG 在线预览**：浏览器原生不支持 DWG，所以要求技术部门同时上传受控 PDF 供车间查阅。
- **单厂部署**：时间统一使用服务器本地时区；如果以后要多工厂部署，需要加组织维度。
- **上线前**：先用测试库导入真实的物料和 BOM，逐个核对成熟机型 BOM 的准确性。齐套结果准不准，取决于 BOM 准不准。

## 六、评审修订与验证记录（2026-10-20）

**修订的 5 条业务规则**：①订单绑定批准图纸版本（升版不自动失效，重大变更才强制暂停）；②2 天改为检查节点，在途按“到货 + 检验转运 ≤ 需求日”判断；③自动重算只分配空闲量，动他单冻结量走“预演 → 审批”；④行级冲销先查批次去向、下游领用、受影响订单，不安全时给退料/退货/补行路径并保留原始记录；⑤在制自制任务和本厂供料外协的原料先认领，成品件与原料不重复计算，外协区分本厂供料与包工包料。

**安全与可靠性**：正式模式（默认）拒绝启动：弱/默认密钥、默认账号密码、演示看板密钥、通配跨域、自动建表；演示灌库只允许 `APP_ENV=demo`；用 `python -m app.cli create-admin` 创建管理员。看板凭密钥访问时 `mode` 参数无效，展示模式由后端只返回允许展示的数据（客户名打码），周计划在展示模式下对密钥访问关闭。登录失败限流。互斥行 + 行锁（`SELECT … FOR UPDATE`）串行化重算、调料审批、锁定预占、收货、检验、领料过账、发货、冲销；到货支持幂等键。

**验证（实测，非推断）**：
- 全部 58 项自动化测试（含第七节的审计回归）在 **SQLite 与 MySQL 8.0** 上通过；干净的 **Python 3.12** 虚拟环境按 requirements 重新安装后，同样两种库上都通过（此过程发现并补上了遗漏的 `openpyxl` 依赖）。
- 7 个评审场景均有测试：同料并发预占不超占、到货重复提交与并发检验不重复入库、已领用后冲销被阻断（退料后才放行）、急单调料保护已领料并记录受影响订单、半成品/自制完工不重复计算原料、图纸升版后在制订单仍用批准版本、部分完工/领料/退料/发货数量闭合；另有事务回滚测试。
- 并发测试做过反向验证：去掉锁后，“并发预占”“并发审批调料”“重复到货”三条测试会失败。
- Alembic 迁移在 MySQL 8 上验证升级、降级、再升级与 `alembic check`；迁移含旧数据回填（旧确认 → 批准版本绑定）。

**尚未验证 / 需要现场确认**：真实物料与 BOM 数据下的齐套准确性；多进程（`--workers 2`）下的登录限流为进程内计数；真实并发量与性能压测；客户现场的网络与权限策略；各物料的“检验/转运天数”需要按实际配置。
