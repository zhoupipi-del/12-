## 事务和分配约定

- 沿用原齐套全局互斥机制，业务 HTTP 写请求在事务入口先取互斥锁，再读/锁业务单据，避免与收货、退料、发货出现相反的锁顺序。GET 等只读请求、鉴权和 AI 辅助查询不持有该业务互斥锁。
- 关键服务入口也执行对应保护。直接调用其他底层服务的扩展代码，必须遵守“先取得齐套互斥锁，再锁业务单据”的写事务约定；不能绕过 API 另写库表。
- MySQL 连接采用 `READ COMMITTED`，避免鉴权已读库后，等待互斥锁的请求继续拿旧的一致性快照计算库存。状态转换仍使用 `FOR UPDATE` 和 `populate_existing`。
- 同一事务内串联服务时，先 flush 合法变更，再刷新锁定对象，避免将刚过账/刚开工的状态覆盖回旧值。
- 任务分配共用齐套既有顺序：人工锁料 → 已开工任务 → 订单冻结 → 未开工任务。任务同组按计划日期、类型、ID 排序。现有订单冻结机制保留；任务获配量由齐套规则计算，不是新增的任务人工锁料单。
- 可领量同时受全生产库可用量和实际出库仓实存约束。不得通过领料或调拨带走其他单据实际占用的库存。

## 老数据与本次边界

1. 空的历史 BOM 快照不能证明当时已经批准免投料，按阻断处理，不自动补成“历史批准版本”。技术应先核实：确无投入才批准免 BOM；确有投入的未开工订单/任务，应维护正确 BOM 后按现有取消、重建流程重新冻结。已开工记录须按受控数据更正方案处理，不直接篡改快照。
2. 本次不批量修正历史上可能已重复完工、超退或账物不符的记录，须先核对库存和流水再制定调整方案。
3. 本轮只修上述四项；真实厂方 BOM/库存试运行、压力测试、生产多实例容量、Excel 模板扩展等尚不据此视作完成。
4. 上轮发现的旧“初始迁移全链 downgrade base 外键索引问题”没有在本次修改。已验证的是最新一步回退与重新升级，不宣称全链回退已修复。
